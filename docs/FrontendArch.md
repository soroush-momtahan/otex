
>[!tip] 1. نگاشت لایه‌های Clean Architecture در فرانت‌اند (Angular / Blazor)
> 1. **لایه Presentation / Endpoint:** کلاس کامپوننت. (فقط گوش دادن به رویدادهای کاربر و نمایش دیتا؛ بدون هیچ منطق بیزنسی).
> 2. **لایه Application / Orchestration:** کلاس Store (در Angular) یا Scoped Service (در Blazor). (مدیر هماهنگی، هندل کردن لودینگ‌ها، و صدا زدن سرویس‌ها).
> 3. **لایه Infrastructure:** سرویس‌های HTTP یا Refit. (فقط تبدیل دیتا به JSON و ارتباط با API، بدون نگهداری State).

>[!tip] 2. نگاشت معماری در محیط Server-Driven (Hydro / Razor)
> 4. **حذف لایه‌های زائد:** لایه‌های Endpoint و Infrastructure کلاینتی کلاً حذف می‌شوند (چون مرز شبکه/HTTP بین فرانت و بک‌اند برداشته شده است).
> 5. **لایه Application (مستقیم):** کلاس `HydroComponent` دقیقاً نقش لایه Application فرانت را بازی می‌کند و مستقیماً Command/Query های لایه Applicationِ بک‌اند (مثل MediatR) را صدا می‌زند.

>[!tip] 3. لایه Domain فرانت‌اند و مدل‌های اختصاصی هر لایه
> فرانت‌اند فاقد Domain بک‌اندی است؛ "دامنه" فرانت‌اند در واقع همان **منطق رابط کاربری (UI Logic)** است. هر لایه مدل‌ها و قوانین ایزوله‌ی خود را دارد:
> 
> **الف) مدل‌های لایه Endpoint / Presentation:**
> - `InputModel`: دیتای خامی که کاربر وارد می‌کند (پیش از تایید سرور).
> - `UiState`: وضعیت‌های گذرای صفحه (مثل باز بودن مودال، تبِ فعال).
> 
> **ب) مدل‌های لایه Application (Store / Hydro):**
> - `ViewModel` یا `AppState`: منبع حقیقتِ تایید شده برای نمایش در UI (حاوی وضعیت‌های بیزنسی مثل CurrentStep یا IsLoading).
> 
> **ج) مدل‌های لایه Infrastructure:**
> - `CommandModel` / `QueryModel` (یا DTOها): مدل‌هایی با ساختار دقیقاً منطبق بر انتظار API بک‌اند.
> - `ErrorModel`: مدل استاندارد خطاها (مثل `ProblemDetails`) برای یکپارچگی مدیریت خطا در کل اپلیکیشن.
> 
> **د) منطق دامنه‌ی فرانت‌اند (Frontend Domain Logic):**
> - **Mappers (مپرها):** توابع خالص (Pure Functions) که وظیفه تبدیل `InputModel` به `CommandModel` را دارند تا لایه‌ها به هم نشت نکنند.
> - **Validators (اعتبارسنج‌ها):** قوانین اعتبارسنجی (مثل FluentValidation در Blazor یا Signal Forms در Angular) که روی `InputModel` اعمال می‌شوند.
> - **Formatters/Calculators:** توابعی که دیتای خام را برای کاربر زیبا می‌کنند (مثلاً تبدیل عدد به فرمت پول، یا محاسبه درصد پیشرفت فرم).

### چرا این چارچوب بی‌نقص است؟
*   **هیچ وابستگی پنهانی وجود ندارد:** کامپوننت نمی‌داند API چه شکلی است (چون `CommandModel` را نمی‌شناسد). API هم نمی‌داند فرم کاربر چه شکلی است (چون `InputModel` را نمی‌شناسد).
*   **مپرها (Mappers) به عنوان چسبِ معماری:** تو با تبدیل `InputModel` به `CommandModel` قبل از ارسال به زیرساخت، باعث می‌شوی اگر فردا روزی بک‌اند تصمیم گرفت ساختار DTO هایش را عوض کند، تو فقط یک تابع Mapper را تغییر دهی، نه کل کدهای HTML و Component ات را!
*   **یکپارچگی ذهنی:** این معماری باعث می‌شود تو با یک **الگوی ذهنی ثابت**، همزمان روی پروژه‌های Angular، Blazor و Razor کار کنی بدون اینکه Context Switching ذهنت را خسته کند.

من به عنوان یک معمار نرم‌افزار، از این سطح دقت و کالبدشکافی تو به شدت لذت بردم. این چارچوب کامل، استاندارد و آماده‌ی استفاده در ابعاد انترپرایز (Enterprise) است!
